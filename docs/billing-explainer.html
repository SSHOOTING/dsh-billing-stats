一次请求的费用骨架

费用 = 未缓存输入 × 输入单价 + 缓存读取 × 缓存读取单价 + 缓存写入 × 缓存写入单价 + 输出（含 reasoning）× 输出单价 + 搜索固定费 × 搜索次数 + 其他可证明的固定费用 峰时请求：token 分项再乘峰时倍率 账户/套餐：对可归因费用乘账户倍率，或由请求级拟合直接覆盖单价

关键区别：“输入 token”不是一个桶。缓存命中的部分必须以供应商返回的 cacheReadTokens / cache_read_input_tokens 为准；重复 query 不能证明命中。输出 token 已包含 reasoning，不能再加一遍。

哪些变量会改变最终金额

上下文长度输入和缓存读取分别计价；长上下文不是线性“看起来贵”，而是每个桶各自乘单价。
缓存命中命中后未缓存输入下降，但缓存读取仍收费；确切命中只能看 usage。
思考/输出reasoning 包含在 output tokens 中；真正影响金额的是最终 output token 数。
峰谷时段官方支持的模型在指定工作时段乘倍率；周末与节假日需单独验证。
搜索/工具搜索可能产生独立辅助模型请求和固定费，不能只按“工具调用次数”记账。

为什么要允许“用户自己的账单拟合”

供应商公开价、控制台 list cost、套餐 allowance、促销折扣和实际扣款可能不是同一个口径。最可靠的做法不是把某个倍率写死，而是：

1. 记录 usage每次请求保存四个 token 桶、时间、模型和搜索次数。
2. 导入账单CSV/JSON/JSONL；请求级或聚合级都可以。
3. 对账先比较总额，再按请求 ID 或 session/turn/step 尝试逐条匹配。
4. 拟合样本少时拟合总倍率；请求级样本充足时拟合分桶单价。
5. 留痕价格档案写入样本数、方法、残差、验证状态，后续可审计。
