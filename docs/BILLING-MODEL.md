# 计费模型与实验边界

## 1. 费用证据优先级

同一个请求只保留一条费用结果，按以下优先级选择：

| 优先级 | 证据 | 含义 | 展示标签 |
|---|---|---|---|
| 1 | 请求级账单明细 | 供应商账单中的该请求实际金额 | 账单明细 |
| 2 | 官方 usage | 供应商返回的 input/cache/output token 数 | 官方用量 |
| 3 | 文本估算 | 可见消息文本和工具定义按字符数折算 token | 文本估算 |
| 4 | 未知 | 缺少可计价内容、模型价格或路由 | 未知 |

高优先级证据会覆盖同一 `session + turn + step` 的低优先级结果，但不会重复计数。
兜底估算只在官方 usage 缺失时启用；它是一种降级显示，不是官方 token 数。

## 2. 四个 token 桶

DSH 上报的 usage 先归一到四个互斥桶：

| 桶 | 字段示例 | 含义 |
|---|---|---|
| 未缓存输入 | `inputTokens` / `uncachedInputTokens` | 没有被自动前缀缓存命中的输入 |
| 缓存读取 | `cacheReadTokens` / `cache_read_input_tokens` | 命中缓存后读取的前缀 |
| 缓存写入 | `cacheWriteTokens` / `cache_creation_input_tokens` | 供应商明确报告写入缓存的 token |
| 输出 | `outputTokens` | 模型输出，已包含 reasoning token |

推理 token 不应重复加；如果供应商只提供一个 output 总数，就按那个总数计费。

## 3. list cost 与 billed cost

- **list cost**：按模型公开单价、峰时倍率、搜索费和汇率算出的价格。
- **billed cost**：在 list cost 上应用账户倍率，或由请求级账单拟合直接覆盖后的金额。

OpenCode Go 的 `allowance` 应理解为该产品账户内的额度消耗/折算值。当前配置里的 `0.6` 只表示“本账户历史观测到的 allowance 约等于 list_cost 的 0.6 倍”，不能解释成供应商全球统一六折，也不能直接说成银行扣款。换账户、换套餐、促销或额度规则变化后必须重新拟合。

## 4. 峰谷

当前内置配置把工作日北京时间 `09:00–12:00`、`14:00–18:00` 作为 DeepSeek Flash 的峰时窗口，倍率 `2×`。周末默认为非峰时。法定节假日需要显式配置日期；没有节假日表时，插件不会擅自猜测。

峰时倍率只作用于明确声明支持它的模型 token 分项。搜索固定费是否随峰时变化，必须由账单实验确认。

## 5. 搜索

搜索请求可能包含两层成本：

1. 搜索辅助模型的 input/output/cache token；
2. 搜索工具的每次调用固定费。

DSH 的一次 `web_search` 工具调用可能拆成多次辅助模型请求，所以“工具调用 1 次”不等于“搜索请求 1 次”。本插件把 shim 的 search ledger 按请求指纹关联回 DSH 会话，并把搜索 token 与搜索固定费分开归因。

当前 `¥0.005 / 搜索请求` 是观测值，标记为待官方账单复核。

## 6. 自动缓存

供应商没有在请求前告诉你“这次一定命中”。可确认的命中信号只有响应 usage 中的 cache read token。常见影响因素包括：

- 前缀是否完全一致；
- 距上次写入/读取的时间；
- 供应商缓存的 TTL 与淘汰策略；
- 同一账户下其他请求是否挤占缓存；
- 模型、路由和协议版本是否发生变化。

因此本项目不从 query 重复、文件重复或时间接近推断缓存命中，也不会在请求前承诺 12/24/36 小时一定命中。TTL 需要用同一长前缀做受控实验，记录不同时间间隔的 cache read token 和账单。

## 7. 自部署

自部署不是 token 单价问题，而是 GPU 小时、电力、闲置率、运维和存储问题。当前只保留 TODO，不在 MVP 中把云 API 单价套到本地模型。
